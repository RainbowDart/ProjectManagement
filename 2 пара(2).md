# Практическая работа №2. Выбор модели для собственного проекта

*(На примере проекта «Система управления задачами», рассматриваемого ранее).*

## Анализ проекта
*   Насколько понятны требования заказчика? Базовые понятны (регистрация, задачи), но детали (какие именно статусы, какие фильтры) могут меняться.
*   Может ли заказчик менять требования? Да, по мере использования прототипа.
*   Можно ли разделить продукт на отдельные функциональные части? Да (модуль пользователей, модуль задач, модуль отчетов).
*   Нужно ли регулярно показывать промежуточные результаты? Да, чтобы заказчик видел прогресс и вовремя корректировал интерфейс.
*   Насколько критичны сроки? Средне. Важнее сделать качественный и удобный продукт, чем сдать сырой релиз.

## Сравнение моделей

| Модель | Как будет организована разработка? | Преимущества | Недостатки |
| :--- | :--- | :--- | :--- |
| Waterfall | Сначала пишем 100% ТЗ, потом БД, потом весь код, потом тесты. | Простота управления. | Заказчик увидит продукт только в конце. Любые изменения — боль. |
| Итерационная | Делаем каркас, затем 3-4 раза дорабатываем его (добавляем статусы, фильтры, улучшаем UI). | Продукт постоянно улучшается. | Есть риск «застрять» в доработках и не выпустить релиз. |
| Инкрементальная | Сначала релизим только регистрацию. Потом добавляем создание задач. Потом отчеты. | Быстрый запуск базовых функций. | Нужна очень грамотная архитектура, чтобы части состыковались. |
| Agile | Работаем спринтами по 1 неделе. В конце спринта показываем заказчику рабочий кусок. | Максимальная гибкость, высокая вовлеченность заказчика. | Требует зрелой команды, сложно прогнозировать бюджет. |

## Выбранная модель и обоснование
*   Выбранная модель: Agile (Scrum).
*   Особенности проекта: Заказчик не имеет четкого технического задания на все элементы интерфейса, но хочет видеть быстрый результат.
*   Преимущества: Мы сможем выпустить MVP (минимально жизнеспособный продукт) с базовым функционалом уже через 2 недели, а затем наращивать функции, опираясь на фидбек реальных пользователей.
*   Ограничения: Заказчик должен быть доступен для обратной связи каждую неделю, иначе преимущества Agile теряются.

## Предварительный план разработки (3 рабочих цикла)

1.  Цикл 1 (Неделя 1): Проектирование БД, реализация API и UI для регистрации, авторизации и создания простейших задач. Демонстрация заказчику.
2.  Цикл 2 (Неделя 2): Добавление возможности редактировать задачи, назначать исполнителей и менять статусы (To Do, In Progress, Done). Демонстрация.
3.  Цикл 3 (Неделя 3): Реализация поиска, фильтрации по статусам и исполнителям. Написание автотестов, исправление багов. Развертывание.
